# Validate Review Comment

## Overview

Скептическая проверка одного замечания код-ревью. Цель — не согласиться и не отвергнуть по умолчанию, а доказать вердикт на конкретном сценарии из реального кода.

## Вход

Замечание идёт в сообщении пользователя сразу после вызова скила: текст ревью-комментария, diff-контекст или ссылка на файл/строку. Если замечание не приложено — попросить его вставить, не придумывать содержание.

## Workflow

1. **Извлечь claim.** Сформулировать в одно предложение, что именно замечание утверждает как проблему. Если формулировка расплывчата — не додумывать, а явно зафиксировать самую сильную разумную трактовку.

2. **Прочитать реальный код.** Открыть указанный файл/строки (Read/Grep/LSP). Никогда не выносить вердикт по пересказу из замечания — только по факту в коде. Если путь/строка не указаны — найти место самостоятельно (Grep/Explore-агент), не гадать.

3. **Попытаться опровергнуть.** Активно искать причину, почему claim ложный:
   - инвариант, который делает сценарий невозможным (валидация выше по стеку, гарантия типа, недостижимая ветка);
   - защита уже существует в другом месте (другой слой, middleware, БД constraint);
   - замечание опирается на устаревшую версию кода/паттерн, которого уже нет;
   - расхождение по стилю/вкусу, а не по корректности.
   Если опровержение найдено и подтверждается кодом — вердикт FALSE POSITIVE.

4. **Попытаться подтвердить.** Если опровергнуть не удалось — построить конкретный сценарий отказа: входные данные/состояние → путь выполнения → неверный результат/паника/утечка/гонка. Обязательно указать, где именно в коде (file:line) рвётся инвариант. Без конкретного сценария вердикт CONFIRMED не выставлять.

5. **Оценить трудоемкость и impact.** Если CONFIRMED — оценить оба измерения независимо:
   - Трудоемкость: trivial (несколько строк, без побочных эффектов) / small (один файл/функция, тесты не меняются) / medium (несколько файлов, нужны тесты) / large (архитектурные изменения, миграции, несколько слоёв).
   - Impact: cosmetic (стиль/читаемость, на поведение не влияет) / bug-risk (некорректный результат в edge-case) / security (уязвимость, утечка, обход проверки) / data-loss (потеря/порча данных, необратимость).

6. **Вынести вердикт.** Формат ответа — эмодзи-маркеры вместо текстовых меток для быстрого визуального сканирования:

```
🔴 Вердикт: CONFIRMED   (🟢 FALSE POSITIVE | 🟡 NEEDS CONTEXT)
Claim: <одно предложение>
Доказательство: <конкретный сценарий отказа с file:line, ЛИБО конкретная причина почему сценарий невозможен>
Трудоемкость: <trivial/small/medium/large — только если CONFIRMED>
Impact: <💄 cosmetic | 🐛 bug-risk | 🔓 security | 💥 data-loss — только если CONFIRMED>
Рекомендация: <⚡ fix now | 📋 backlog | ⏭ skip — только если CONFIRMED>
```

Маркер вердикта: 🔴 CONFIRMED / 🟢 FALSE POSITIVE / 🟡 NEEDS CONTEXT.
Маркер Impact: 💄 cosmetic / 🐛 bug-risk / 🔓 security / 💥 data-loss.
Маркер Рекомендации: ⚡ fix now / 📋 backlog / ⏭ skip.

Рекомендация — сведение Трудоемкости и Impact в одно решение, не отдельная оценка:
   - `⚡ fix now` — security/data-loss любой трудоемкости, либо bug-risk trivial/small.
   - `📋 backlog` — bug-risk medium/large, либо cosmetic large.
   - `⏭ skip` — cosmetic trivial/small (правится по ходу, отдельного цикла не стоит).

`NEEDS CONTEXT` — только если код физически недоступен для чтения (внешняя система, отсутствующий файл) или замечание ссылается на решение, которое может быть только на усмотрение пользователя (архитектурный trade-off без явного правила в CLAUDE.md/AGENTS.md). Не использовать как способ уйти от вердикта при лени проверить.

7. **Предложить план доработок (только если CONFIRMED).** Сразу после вывода вердикта вызвать AskUserQuestion с вопросом "Создать план доработок?" (варианты: да / нет). Не задавать этот вопрос при FALSE POSITIVE или NEEDS CONTEXT — там чинить нечего или не хватает информации.
   - Если да — перейти в режим планирования (EnterPlanMode) и спланировать реализацию исправления по замечанию: какие файлы менять, какой подход, как проверить (тесты/lint/сборка). Использовать доказательство и file:line из вердикта как отправную точку, не пересобирать анализ заново.
   - Если нет — на этом остановиться, реализацию не начинать.

## Правила

- Не соглашаться с замечанием только потому, что оно оформлено уверенно или пришло от ревьюера/линтера — доказательство обязательно.
- Не отвергать замечание только потому, что "выглядит как nit" — если конкретный сценарий отказа строится, это CONFIRMED вне зависимости от серьёзности тона исходного текста.
- Один раунд опровержения/подтверждения должен использовать реальный код проекта (Read/Grep/LSP), а не общие рассуждения о том, "как обычно бывает".
- Если замечание касается нескольких независимых утверждений — разбить на отдельные claim'ы и вынести вердикт по каждому.
- Никогда не начинать правки кода сразу после CONFIRMED без явного "да" на вопрос о плане.
